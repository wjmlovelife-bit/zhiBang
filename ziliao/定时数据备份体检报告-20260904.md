## 1. P0 问题：gzip 失败，数据库 dump 没压缩

### 现象
- `db/2026-09-03.dump`（185 KB，**未压缩**，mtime `2026-09-04 00:00:01`）—— 这是 9/3 凌晨 0 点自动跑的产物
- `db/2026-09-03.dump.gz`（73 KB，mtime `2026-09-03 10:22`）—— 这是 9/3 上午手动测试时压的
- 主日志明确说：`'gzip' is not recognized as an internal or external command` + `FAILED gzip exit 9009`

### 根因
`backup-db.bat` 第 27 行直接写 `gzip -f "..."`，**没写绝对路径**。任务计划程序以 `SYSTEM` 身份运行，`SYSTEM` 的 PATH 不含 Git Bash 的 `gzip.exe`：
```
gzip 实际位置：C:\Users\魏博\.workbuddy\binaries\PortableGit\...\gzip.exe
SYSTEM 用户 PATH：默认不含此目录
```

**但是手动跑能成功**（9/3 10:22 上午那次），因为当前用户 PATH 含 Git Bash 目录。

### 后果
- 数据库 dump 185 KB vs 压缩后 73 KB = 1.4 MB 差（数据小，看不出明显问题）
- 真正的风险：**当数据量增长到 100 MB / 1 GB 时，未压缩的 dump 会占满备份目录**
- 7 天清理逻辑（`forfiles /d -7` 删 `*.dump.gz`）**只清理 .gz 文件**，所以 `2026-09-03.dump` 这种未压缩文件**永远不会被清**——备份目录会一直膨胀

### 修复（5 分钟）
1. 改 `backup-db.bat` 第 27 行，**用绝对路径**：
   ```bat
   "C:\Users\魏博\.workbuddy\binaries\PortableGit\versions\1.2.0\usr\bin\gzip.exe" -f "%BACKUP_DIR%\db\%DATE%.dump"
   ```
2. 改清理逻辑：把 `forfiles /d -7 /m "*.dump.gz"` 改为 `forfiles /d -7 /m "*.dump*"`（同时清 .dump 和 .dump.gz）
3. 手动跑一次 `backup-master.bat` 验证
4. 把这次失败的 `2026-09-03.dump`（185 KB）压缩成 .gz 留作备份（用绝对路径调用 gzip）

### 建议（更稳）
直接用 7z / PowerShell 压缩，不依赖外部 PATH：
```bat
powershell -NoProfile -Command "Compress-Archive -Path '%BACKUP_DIR%\db\%DATE%.dump' -DestinationPath '%BACKUP_DIR%\db\%DATE%.dump.zip' -Force"
```
7z 压缩率比 gzip 还高一点（zip deflate 与 gzip deflate 等价，但 7z LZMA 更高），且 PowerShell 是 Windows 内置，零外部依赖。

## 2. P1 问题：Windows 任务计划程序没注册 / 状态未知

### 现象
- `master.bat` 末尾有自动注册任务（`schtasks /create ... /sc daily /st 00:00:00 /ru SYSTEM /rl HIGHEST`）
- 但 9/3 凌晨 0 点 `2026-09-03.log` 只有 251 字节——说明 master.bat 跑时**没注册成功 / 没执行到注册那段**（其实 gzip 失败 master.bat 就退出了，但 master.bat 用的是 `call` + 不检查 errorlevel，所以应该继续跑）
- 进一步：手动 `schtasks /query /tn "zhibang-nightly-backup"` 沙箱里跑不出来结果（cmd 输出被截断）
- 但 `db/2026-09-03.dump` mtime 是 9/4 00:00:01——说明**任务确实跑了**（只是 gzip 步骤失败）

### 判断
**任务应该是注册了**（毕竟 00:00 那个时间点是任务计划程序才可能的精度，手动不会恰好那个时间点）。但因为系统是 `SYSTEM` 跑的，**0 点那个时间点"刚好"就是 task 触发**。

### 风险
如果任务没注册成功，9/3 上午手动跑过 master.bat 一次（10:22 mtime 的 dump.gz 证明），那么 9/3 凌晨 00:00 那个 185KB 的 dump 可能是**昨天（9/3）用户手动触发的**，而不是任务计划自动跑的。需要确认。

### 验证方法（你在宿主机跑）
```cmd
schtasks /query /tn "zhibang-nightly-backup" /v /fo LIST
```
应该看到：
- 任务名：`zhibang-nightly-backup`
- 下次运行时间：2026-09-05 00:00:00
- 上次运行时间：2026-09-04 00:00:00（状态 0x0 = 成功 / 或 0x1 = 失败）
- 状态：就绪

如果不存在就手动跑一次 `backup-master.bat`（以管理员身份），让它自动注册。

## 3. P1 问题：昨晚的 dump 缺 mustResetPassword 字段

### 现象
- 9/3 16:23 我加了 `mustResetPassword` 字段到 schema（`prisma db push` 已推）
- 9/4 00:00 自动备份生成 `2026-09-03.dump`（185 KB，PGDMP 头）—— 看起来成功
- 但**方案第 10 节明确说**：「任何时候改了**数据库结构**（schema.prisma 变更）→ 立即**手动跑一次 `backup-master.bat`**，确保新表结构被备份」

### 风险评估
**实际没事**：9/4 00:00 的 dump 是在 9/3 16:23 schema 变更**之后**的，dump 应该已经包含新字段。

但需要验证：
```bash
pg_restore -l D:\github\xiangmutest\opencode\zhibangDataBackup\db\2026-09-03.dump | grep -i "mustresetpassword\|sysuser"
```
看 dump 里是否含 `ALTER TABLE "SysUser" ADD COLUMN "mustResetPassword"...` 这种语句。

### 风险
- 如果是 prisma `db push`（不是 `migrate`），dump 里**不**会含 ALTER 语句（pg_dump 是逻辑 dump，数据 + schema 全量，但 prisma push 后表的列定义直接生效，dump 看到的是最终 schema）
- 所以这个不是真问题，**但下次 schema 变更需要立刻手动跑一次**（按方案第 10 节）

### 建议
在 `crm系统说明文件.md`（或新建 `运维清单.md`）里加一条：
> 任何时候 `prisma db push` 跑过 → 立刻手动跑一次 `D:\github\xiangmutest\opencode\zhibangDataBackup\backup-master.bat` → 验证 `db/<今天>.dump.gz` 是新的

## 6. 验证脚本

把下面这段贴到 PowerShell，能一键查"任务计划 + 备份产物 + 日志"全状态：

```powershell
# 任务计划程序
Write-Host "=== 任务计划 ===" -ForegroundColor Cyan
try {
    Get-ScheduledTask -TaskName 'zhibang-nightly-backup' | Format-List TaskName, State, Author
    Get-ScheduledTaskInfo -TaskName 'zhibang-nightly-backup' | Format-List LastRunTime, NextRunTime, LastTaskResult
} catch { Write-Host "任务未注册" -ForegroundColor Red }

# 备份产物
Write-Host "`n=== 备份产物 ===" -ForegroundColor Cyan
$backupDir = 'D:\github\xiangmutest\opencode\zhibangDataBackup'
Get-ChildItem "$backupDir\db" -ErrorAction SilentlyContinue | Format-Table Name, Length, LastWriteTime -AutoSize
Get-ChildItem "$backupDir\logs" -ErrorAction SilentlyContinue | Format-Table Name, Length, LastWriteTime -AutoSize
Get-ChildItem "$backupDir\uploads" -ErrorAction SilentlyContinue | Measure-Object | Select-Object Count, @{N='Size(MB)';E={[math]::Round(($_.Sum / 1MB), 1)}}

# 最近一次 dump 是否压缩成功
Write-Host "`n=== 最近 dump ===" -ForegroundColor Cyan
$latest = Get-ChildItem "$backupDir\db" -Filter "*.dump*" | Sort-Object LastWriteTime -Descending | Select-Object -First 2
$latest | Format-Table Name, Length, LastWriteTime -AutoSize
$dumpExists = Test-Path "$backupDir\db\2026-09-03.dump"
$gzExists   = Test-Path "$backupDir\db\2026-09-03.dump.gz"
if ($gzExists) { Write-Host "✅ 最新 dump 已压缩" -ForegroundColor Green }
elseif ($dumpExists) { Write-Host "❌ 最新 dump 未压缩！需要手动 gzip" -ForegroundColor Red }
```

预期输出（修复后）：
- `任务名: zhibang-nightly-backup | 状态: Ready`
- `上次运行: 2026-09-04 00:00:00 | 退出码: 0`
- `最近 dump: 2026-09-03.dump.gz, 73 KB`
- ✅ 压缩成功

## 7. 长期建议

1. **监控告警**：备份日志里出现 FAILED 应该主动通知（邮件/企微）。当前只有日志本地留存，**没人看就等于没备份**。
2. **保留策略升级**：当前 7 天偏短，业务数据建议 ≥ 30 天；可加每周日 1 个"月度快照"（保留 12 个月）。
3. **异地备份**：本地备份只防"误删/代码 bug"，不防"硬盘坏/电脑被偷"。建议每周把 `db/` 同步到 OneDrive/网盘/NAS。
4. **恢复演练**：至少每季度做一次"从 dump 恢复到测试库 + 改 1 条数据看是否生效"的演练，验证备份真的能恢复。
5. **加密**：dump 文件含明文业务数据（客户/合同/报价），建议加 7z 加密或 GPG。
