### 0.1 结论：先修测试可信度，再增加关键业务回归

当前不是“完全没有测试”。仓库同时存在四种入口：

| 位置 | 实际入口和作用 | 当前主要问题 |
| --- | --- | --- |
| backendTest | Jest；业务服务单元测试、common 工具测试、直接调用服务的真 PostgreSQL 集成测试 | 默认混跑数据库；test:unit 漏掉 common；构造依赖落后于源码；部分断言吞错 |
| backend/test | Node .mjs；向已经运行的服务发 HTTP 请求 | 创建失败可降级 warn；某些成功条件也接受 4xx/5xx；缺少二进制响应解析；账号和用例相互影响 |
| frontendTest | Vitest；当前较多的前端测试 | 部分复制函数；过时的 JSON/PDF mock；仅测试浏览器存储本身；缺少真实页面提交链路 |
| frontend/tests/unit | 前端目录内另一套 Vitest | 与 frontendTest 有交叉，但默认不会互相发现；旧指令用例只模拟表达式 |

不能用 README 或旧《测试用例建议.md》中的“全绿”“多少用例”作为当前运行结论。文件存在、静态 it 数量、运行时展开后的用例数量、通过数量是四件不同的事。循环生成的测试还会使静态计数和运行数量不同。本轮实际执行范围见最后的复核记录。

### 0.2 本手册把实施分成三组

| 分组 | 内容 | 实施前提 |
| --- | --- | --- |
| A：可以先修的测试问题 | 测试入口、依赖注入、旧 JSON 断言、axios 默认配置断言、PDF 边界 mock、冻结时间、严格错误断言 | 维持现有业务行为；不能为了让旧测试通过而把已修复业务代码改回去 |
| B：随已确认业务修复加入的回归 | 两类 Excel 的内容/合并规则、报价更新原子性、项目局部金额、跟进日期等 | 测试使用正确预期；当前源码有缺陷时允许明确失败，与对应业务修复同组实施 |
| C：业务规则或迁移未确认的测试 | 新导入批次协议、日程提交/版本规则、历史金额重算、联系人物理删除、统计指标切换 | 只列场景和待定输入，不导入尚不存在的工具/模型，不把候选规则写成当前必须通过的断言 |

《智邦CRM逐文件修改手册.md》第 0.0 节的暂缓状态继续有效。本手册不是批准执行原手册中已暂缓的业务改造。

**不要做的事：** 为了全绿把正确回归改成“成功或任意失败都可以”；用 it.skip 隐藏没有编号的问题；在 catch 中写 expect(true).toBe(true)；把一个内存 mock 回调说成数据库回滚证明；把假的 HTML/PDF 边界替身说成真实 Chromium 渲染成功。

## 2. 先修改测试入口，不让普通测试隐式连接数据库

### 2.1 修改 backendTest/package.json 的 scripts

只替换 scripts 对象，保留 name、version、依赖等其他内容：

```json
{
  "test": "jest --selectProjects unit --runInBand",
  "test:unit": "jest --selectProjects unit --runInBand",
  "test:integration": "jest --selectProjects db --runInBand",
  "test:all": "npm run test:unit && npm run test:integration",
  "test:types": "tsc --noEmit -p tsconfig.json",
  "smoke": "npm run smoke:customer && npm run smoke:sales-schedule && npm run smoke:permission",
  "smoke:customer": "node smoke/smoke-customer.mjs",
  "smoke:sales-schedule": "node smoke/smoke-sales-schedule.mjs",
  "smoke:permission": "node smoke/smoke-permission.mjs"
}
```

理由：common 工具测试必须进入默认入口；数据库测试由明确命令选择；不再用 --forceExit 掩盖未关闭连接。三个 smoke 都依赖已经运行的后端，不能当作纯单元测试运行。本轮保留 permission 入口，不改变其中权限业务规则。

backend/package.json 中已有 test=jest，但 backend 内没有与 backendTest 等价的 Jest 配置。若希望在 backend 目录运行统一单元测试，把该脚本改为 `npm --prefix ../backendTest run test:unit`，不让它扫描各种临时 test-*.ts 文件。backend/test/run-all.mjs 仍是另一个 HTTP 入口。

### 2.3 修改 backendTest/src/setup/jest.setup.ts

默认单元测试 setup 不再设置 DATABASE_URL，不连接数据库。保留其他已有测试初始化即可；本轮不更改鉴权策略。不要在全局固定当前时间，否则所有测试共享一个隐藏业务假设。

### 2.4 新增 backendTest/src/setup/db-env.ts

```ts
const connection = process.env.TEST_DATABASE_URL;
if (!connection) {
  throw new Error('数据库集成测试需要显式设置 TEST_DATABASE_URL');
}

const database = decodeURIComponent(new URL(connection).pathname.slice(1));
if (!database.endsWith('_test')) {
  throw new Error('数据库集成测试只允许使用名称以 _test 结尾的测试库');
}

process.env.DATABASE_URL = connection;
```

然后从全部九个 integration 文件的 beforeAll 中删除硬编码 `process.env.DATABASE_URL = ...`，否则会覆盖这里的配置。保留显式的 prisma.$connect()，并在 afterAll/afterEach 关闭资源。数据库名称约束是测试隔离的最低检查，不代表检查了库里所有数据。

原有全表 deleteMany({where:{}}) 加 catch(() => {}) 不再保留：改为只删除本次 fixture 的 ID，并按外键顺序清理；错误应抛出，让测试报告为 fixture 失败。不能清理失败后带着旧数据继续测。

### 2.5 依赖与 lock 文件

本轮在 Node 24.19.0 / npm 11.9.0 的隔离快照中执行 backendTest 的 npm ci，安装阶段报告 package-lock 缺少若干 @babel/traverse、@babel/types、istanbul-reports、semver 等条目，尚未进入 Jest。此结论有环境边界，不推断所有 npm 版本必定相同。

实施时在选定的 Node/npm 版本下，先运行 `npm install --package-lock-only --ignore-scripts` 同步 lock，再检查差异并执行 `npm ci --ignore-scripts`。不要删除 lock 后盲目升级所有依赖。四个目录分别管理自己的 package-lock，不手工复制 node_modules。

本轮部分已有 lock 的 tarball 地址指向当前云环境未允许的镜像域，原始完整安装未成功，不能声称已经在原安装环境跑全套。后文隔离复核使用允许的 npm 官方源和选定版本，详细边界在复核记录中列出。

## 3. 统一后端测试的构造依赖和事务替身

以下三个 setup 文件的完整建议代码在后面的“可复制代码”中。先新增 service-fixtures.ts，替换 prisma-mock.ts，再修改各 spec 的实例化方式。

### 3.1 backendTest/src/setup/prisma-mock.ts

把 `DeepMockProxy<any>` 换成基于真实 PrismaClient 的类型适配，删除 `depth:2`；保留旧 setMock/setMockError/resetMockPrisma API，减少无关迁移。新增 bindTransaction(root)，返回单独的 tx 替身。

本轮额外用 tsc 检查时发现，直接深度 mock PrismaClient 会触发 Prisma groupBy 泛型与 jest-mock-extended 3 在 TypeScript 5.9 下的 TS2615 递归类型错误。完整代码在适配层只将 groupBy 简化成 unknown 入参/unknown[] 输出，其他 CRUD 仍使用真实客户端类型；工厂边界用 mockDeep<unknown>() 转换为该适配类型。事务 mock 同样处理。将来测试 groupBy 时必须明确断言分组字段、筛选条件和返回内容，不把这一方法的简化静态类型说成完整 Prisma 类型保证。

数组事务通过 Promise.all 返回 mock 结果；交互事务执行传入回调并传入 tx。这个 helper **只模拟调用协议，不实现回滚、不实现隔离级别、不实现行锁**。回滚必须由真数据库用例验证。

不要把一个 mockResolvedValue([total,items]) 当作所有事务的通用处理：业务代码进入回调事务后，回调根本不会执行，测试却可能只检查 `$transaction` 被调用，从而假通过。

### 3.2 backendTest/src/setup/service-fixtures.ts

新增 makeLogger、makeServiceMocks、loggerProviders。PDF 和 cache 是边界替身；每个 beforeEach 都重新创建，避免前一个用例的 mockResolvedValueOnce 泄漏。

```ts
mock = makeMockPrisma();

```

改为：

```ts
const deps = makeServiceMocks();

service = new QuotationService(mock as any, deps.pdf, deps.logger);
```

```ts
    providers: [
      QuotationService,
```

```ts
import { PdfService } from '@app/common/pdf/pdf.service';
import { makeServiceMocks, loggerProviders } from '../setup/service-fixtures';
```

```js
export async function reqBinary(path, { token, base = BASE } = {}) {
  const headers = token ? { Authorization: 'Bearer ' + token } : {};
```

### 6.5 新增 backend/test/cases/schedule-export.mjs

```js
import assert from 'node:assert/strict';
import * as XLSX from 'xlsx';

export const name = '日程导出内容';
export async function run(ctx) {
  for (const [module, sheetName, lastColumn] of [
    ['weekly-schedule', '周日程', 'G'],
    ['sales-schedule', '销售日程', 'J'],
  ]) {
    const query = new URLSearchParams({ weekStart: '2026-09-14' });
    const response = await ctx.reqBinary(`/${module}/export?${query}`, {
      token: ctx.tokens.admin,
    });
    assert.equal(response.status, 200);
    assert.match(response.headers.get('content-type') || '', /spreadsheetml/);
    assert.match(response.headers.get('content-disposition') || '', /filename/i);
    const workbook = XLSX.read(response.buffer, { type: 'buffer' });
    assert.ok(workbook.SheetNames.includes(sheetName));
    const sheet = workbook.Sheets[sheetName];
    assert.equal(sheet.C4?.v, '上下午');
    const merges = (sheet['!merges'] || []).map((range) => XLSX.utils.encode_range(range));
    assert.ok(merges.includes(`C1:${lastColumn}1`));
    ctx.case.ok(sheet.C4?.v === '上下午' && merges.includes(`C1:${lastColumn}1`),

}
```

```ts
import * as XLSX from 'xlsx';

export function readSheet(buffer: Buffer, sheetName: string): XLSX.WorkSheet {
  expect(Buffer.isBuffer(buffer)).toBe(true);
  const workbook = XLSX.read(buffer, { type: 'buffer' });
  expect(workbook.SheetNames).toContain(sheetName);
  return workbook.Sheets[sheetName];
}

export function valueAt(sheet: XLSX.WorkSheet, address: string): unknown {
  return sheet[address]?.v ?? '';
}

export function mergeNames(sheet: XLSX.WorkSheet): string[] {
  return (sheet['!merges'] ?? []).map((range) => XLSX.utils.encode_range(range));
}

export function assertValidMerges(sheet: XLSX.WorkSheet) {
  expect(sheet['!ref']).toBeDefined();
  const bounds = XLSX.utils.decode_range(sheet['!ref']!);
  const ranges = sheet['!merges'] ?? [];
  for (let i = 0; i < ranges.length; i++) {
    const a = ranges[i];
    expect(a.s.r).toBeGreaterThanOrEqual(bounds.s.r);
    expect(a.s.c).toBeGreaterThanOrEqual(bounds.s.c);
    expect(a.e.r).toBeLessThanOrEqual(bounds.e.r);
    expect(a.e.c).toBeLessThanOrEqual(bounds.e.c);
    expect(a.s.r).toBeLessThanOrEqual(a.e.r);
    expect(a.s.c).toBeLessThanOrEqual(a.e.c);
    for (let j = i + 1; j < ranges.length; j++) {
      const b = ranges[j];
      const overlaps = a.s.r <= b.e.r && b.s.r <= a.e.r &&
        a.s.c <= b.e.c && b.s.c <= a.e.c;
      expect(overlaps).toBe(false);
    }
  }
}
```

## 9. 推荐实施顺序与运行命令

以下命令从仓库根目录执行，示例使用 Windows PowerShell。先应用 A 组测试修正，再与业务修复同组加入 B 组回归；C 组保持暂缓。不要先粘贴所有回归文件，再把预期失败误认为基础设施没修好。

1. 修 backendTest 的 package scripts/Jest 项目配置、setup、fixture 与构造依赖；先确认纯单元入口不会启动数据库测试。
2. 修前端旧 JSON 断言、PDF mock、request.defaults 断言，加入真实销售日程 behavior.spec。

4. 两份 Excel 内容测试与导出修复一起实施；报价事务单元/数据库回归与最小事务修复一起实施。
5. 在明确的测试库中运行数据库测试；再运行真实 HTTP 入口，检查二进制响应。
6. 统计指标、历史金额、新导入/日程模型等候选规则保持暂缓，待前提核实后再加入对应测试。

### 11.2 最终采用与暂缓的理由

采用测试基础设施修正，因为缺依赖、旧预期、恒真断言和复制函数会直接削弱测试的保护作用，而且可以在维持业务行为的前提下纠正。

采用 Excel 内容、报价原子性等正确回归方案，因为它们能在现有缺陷上失败，并能在隔离副本的对应修复上通过，已经证明能识别目标问题。真数据库回读仍需要另外执行，不能用单元通过代替。

暂缓历史金额、迁移、新状态、新导入协议和统计口径的强制断言，因为这些业务前提在原手册中尚未确认。测试不能替你做业务决定，也不能为了凑覆盖率先创建新字段或回填历史数据。

保留已有真实源码测试和暂未迁移的独有场景，因为“有重复目录”不等于“其中所有断言都无价值”。后续迁移按场景核对，不按文件数删减。
